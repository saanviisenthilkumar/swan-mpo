# SWAN-MPO v1.3.1 — release candidate

SWAN-MPO is a transparent scoring layer for safety-aware, affinity-normalized multi-parameter optimization. The standard workflow starts from **raw upstream candidate-docking, ADME/property, and toxicity/liability outputs**. Users do **not** calculate SWAN domain scores themselves.

> **Release-candidate status:** the frozen model, bundled calibration, raw-input scoring path, symmetry-aware RMSD path, validation, audit outputs, and regression suite are implemented. Before this release is made public, an actual AutoDock Vina **1.2.7** reference-redocking run must pass on an independent local machine. `swan-mpo verify --check-vina` and `swan-mpo verify --vina-config ...` are provided for that terminal test.

## Scientific automation boundary

Researchers provide:

- candidate **grid-level docking results** generated by their docking workflow;
- raw SwissADME-compatible physicochemical/ADME outputs;
- raw ProTox-compatible toxicity/liability predictions, including endpoint confidence;
- for a new target, a prepared receptor PDBQT, prepared native/reference-ligand PDBQT, and a justified redocking box.

SWAN-MPO then performs:

1. input-schema and value validation;
2. safety desirability calculation from LD50, toxicity class, and confidence-coded organ-toxicity endpoints;
3. ADME desirability calculation from the frozen physicochemical/property rules;
4. panel-specific liability calculation from the raw BBB/neurotoxicity/Complex-I inputs used by the locked model;
5. candidate docking aggregation to the **median ΔG across the configured grid centers** for every compound-target block;
6. target-specific reference calibration;
7. reference-normalized target-level binding desirability;
8. exclusion of comparative-only targets from primary BestNode;
9. BestNode selection within each panel;
10. equal-weight geometric integration of safety, ADME, BestNode binding, and liability;
11. ranks, intermediate desirabilities, warnings, hashes, versions, and audit metadata.

SWAN-MPO **does not** call SwissADME or ProTox and does **not** automate candidate-compound docking. Those remain upstream scientific procedures. SWAN-MPO **can** run AutoDock Vina for reference/native-ligand redocking used to calibrate new targets.

## Install and verify

Quick core installation:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
pytest -q
swan-mpo verify
```

For the pinned CLI/reference-redocking environment, see `environment.yml`. The audited upstream RDKit/Open Babel versions are recorded separately in `docs/ENVIRONMENTS.md` because they are not CLI runtime dependencies and were not one monolithic environment. Vina 1.2.7 is enforced when requested for reference-redocking verification.

## One-command demo

```bash
swan-mpo score --demo --output-dir demo_results
```

This runs a **bundled synthetic raw-input regression example** through ADME, safety, liability, target calibration, BestNode, and final scoring. It is intentionally not labeled as a Muricatacin reproduction because the repository will not fabricate manuscript raw predictor inputs that have not been independently source-verified.

For a compact installation check:

```bash
swan-mpo verify
```

To require the exact local Vina version:

```bash
swan-mpo verify --check-vina
```

## Standard scoring

```bash
swan-mpo validate \
  --docking candidate_docking.csv \
  --adme swissadme.csv \
  --toxicity protox.csv \
  --config published-oncology

swan-mpo score \
  --docking candidate_docking.csv \
  --adme swissadme.csv \
  --toxicity protox.csv \
  --config published-oncology \
  --output-dir results
```

The published oncology configuration uses the frozen, audited calibration table for its nine study targets. A researcher can inspect it with:

```bash
swan-mpo show-published-calibration
```

## New-target reference redocking

```bash
swan-mpo redock-reference \
  --targets-config configs/my_target_redocking.json \
  --require-vina-1-2-7 \
  --output-dir redocking_results
```

The redocking runner retains Vina commands/logs, mode energies, symmetry-aware fixed-frame heavy-atom RMSDs, calibration decisions, and file hashes. See `docs/VINA_REFERENCE_REDOCKING.md`.

## Score outputs

Each standard score run writes:

- `compound_safety_adme_desirabilities.csv`
- `panel_liability_desirabilities.csv`
- `target_level_binding.csv`
- `target_calibration_used.csv`
- `swan_panel_scores.csv`
- `warnings.csv`
- `run_metadata.json`
- `run_manifest.json`
- `run.log`

The audit tables expose raw inputs and intermediate desirabilities so a user can trace a final rank back through the calculation.

## Model transparency

```bash
swan-mpo explain-model
swan-mpo explain-model --sources
```

The second command reports the provenance of the frozen thresholds and explicitly distinguishes literature-grounded preferred regions from SWAN-MPO design anchors. See `docs/THRESHOLD_PROVENANCE.md`.

## Published calibration classes

- strict top-pose: Bcl-2, AR, PI3Kα, AKT1
- generated-mode recovery: mTOR, 5AR2
- comparative-only and excluded from primary BestNode: EGFR, Caspase-3, Complex I

### mTOR real-Vina integration check using historical parameters

After verifying AutoDock Vina 1.2.7, users with the frozen SWAN-MPO development source tree can generate a local, git-ignored canonical 4JSP/mTOR redocking config with:

```bash
python scripts/make_mtor_real_vina_config.py
swan-mpo verify --vina-config my_real_vina_mtor.json --output-dir real_vina_verification --report real_vina_verification_report.json
```

The helper uses the frozen tight-native-box parameters rather than the 40 Å candidate-screening box. The structural PDBQT files themselves are not redistributed by this repository.
